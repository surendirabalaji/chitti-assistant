# Learning path

Hands-on plan: you write the code, the assistant explains, hints, and reviews. Each lesson has a goal, the concepts, what you write, how to check it, and questions to answer in your own words (keep your answers; they become your PROCESS_LOG narrative).

## Who writes what

Six days is tight, so not everything can be hand-written. You write the parts that carry the grade and the ideas; boilerplate is generated and then explained to you line by line.

| Piece | Mode | Why |
|---|---|---|

| Router plugin hooks, logging, held reply | **You write** (guided) | Core routing behaviour |
| Unit tests (all router/skill lessons) | **Generated by assistant** at the student's request (Nov 12); student reviews and runs them | Student decision to save time; tests must cover spec rows, boundaries, rule order, and open questions as `it.todo` |

| focus-finder skill | **You write** | Your original published skill |
| Snapshot/restore script | **Guided** | Correctness matters (SQLite backup, atomic upload) |

## Tools you will use

- TypeScript on Node 24.22.1. Node 24 runs `.ts` files directly by stripping types, as long as you use only "erasable" syntax: no `enum`, no `namespace`, no parameter properties. Use union types like `type Target = "local" | "cloud" | "held"` instead of enums.
- Tests with **Vitest** (student's choice, Nov 11; replaces the original `node:test` plan): a pinned devDependency installed with `--save-exact --before=2026-10-30` and a committed `package-lock.json`. Run with `npm test` → `vitest run`. Imports: `import { describe, it, expect } from "vitest";`. Vitest transforms TypeScript itself, so a passing test does **not** prove Node's type stripping can run the file: keep erasable syntax and explicit `.ts` import extensions. (Correction Nov 12: OpenClaw loads local `.ts` plugin entries with its own runtime transformer, not Node type stripping. Erasable syntax is still the safe choice.)
- Reading OpenClaw's own types: `OC=$(npm root -g)/openclaw` then `grep -rn "before_model_resolve" "$OC" --include=*.d.ts | head`.

## Part A: Router (target: Wed evening to Thu)

### Lesson A1: Project skeleton (30 min)
**Goal:** a `router/` folder you can run tests in.
**Concepts:** `package.json` with `"type": "module"`, ES module imports, devDependencies pinned with a lockfile, Vitest (`vitest run` vs watch mode).
**You write:** `router/package.json` (name, private, type module, a `test` script), install Vitest pinned, `router/src/`, `router/test/`, and one trivial test that asserts `1 + 1 === 2`.
**Check:** `cd router && npm test` shows 1 passing test; `package-lock.json` exists; the Vitest version in `package.json` has no `^`.
**Questions:** Why `"type": "module"`? Which files does Vitest pick up by default, and why `vitest run` instead of `vitest`?

### Lesson A2: The decision function, one rule (45 min)
**Goal:** a pure function that decides local vs cloud for one message.
**Concepts:** pure functions (same input → same output, no side effects), why routing logic should be pure (testable without OpenClaw), TypeScript union types, table-driven tests.
**You write:** `router/src/decide.ts` exporting
```ts
export type Target = "local" | "cloud" | "held";
export interface Decision { target: Target; rule: string; }
export function decide(message: string): Decision { /* TODO */ }
```
Rule: if the message is at most 200 characters and contains no reasoning word ("step by step", "explain why", "analyze", "compare", "plan") → `{ target: "local", rule: "simple-task" }`, otherwise `{ target: "cloud", rule: "reasoning-heavy" }` or `"default-cloud"`.
Tests in `router/test/decide.test.ts`: a list of `[message, expectedTarget, expectedRule]` rows and one loop.
**Check:** "What is 12 times 9?" → local; "Explain step by step why the sky is blue." → cloud; a 300-character message → cloud; case-insensitive match ("STEP BY STEP").
**Questions:** Why is the decision a separate pure function instead of living inside the hook? What breaks if matching is case-sensitive?

### Lesson A3: Reading the OpenClaw plugin API (45 min)
**Goal:** know exactly what your hook receives and must return, from the installed code.
**Concepts:** reading `.d.ts` files, finding exported types, comparing docs with the installed version.
**Done by the assistant at the student's request (Nov 12); results in STATUS.md "Plugin API".** Originally: find the plugin entry helper and the `before_model_resolve` event and result types in the installed package; find how a plugin declares its manifest and how a local plugin is installed (`openclaw plugins --help`). Write what you found in STATUS.md under "Verified facts" (field names, return shape, install command).
**Check:** you can answer: what fields does the event have, and which field names override provider and model?
**Questions:** Why trust the installed types over the docs website?

### Lesson A4: The first plugin (1–1.5 h)
**Goal:** OpenClaw automatically sends short messages to Gemma.
**Concepts:** plugin entry and registration, hooks as callbacks, returning an override, model references (`ollama/gemma4-a3:e2b`, `openai/gpt-6-astra`).
**You write:** `router/src/index.ts`: the plugin entry that registers `before_model_resolve`, calls your `decide()`, and returns the override for the chosen model. Plus the manifest the installer needs (from A3).
**Check:** install it, restart the gateway, and in one chat without `/model`: "What is 12 times 9?" is served by Gemma, "Explain step by step why the sky is blue." by ChatGPT. Save evidence.
**Questions:** What happens if the hook throws an error? What happens if it takes 30 seconds?

### Lesson A5: Decision logging (45 min)
**Goal:** one JSON line per decision, no message text.
**Concepts:** structured logging, why metadata only (privacy and the requirements), request ids linking lines.
**You write:** a `logDecision()` helper in `router/src/log.ts` printing `{ component: "a3-router", kind: "route_decision", ts, requestId, rule, target, model }` with `console.log(JSON.stringify(...))`. Test that the output never contains the message.
**Check:** gateway output shows one line per message; grep for a word from your message finds nothing.
**Questions:** Why JSON instead of plain text? Why must message text never be logged?

### Lesson A6: All six rules (1–1.5 h)
**Goal:** the full rule table from ROUTER_SPEC.md, still pure.
**Concepts:** rule precedence (first match wins), word-boundary matching with regular expressions, passing state in (`localHealthy`, `sessionSizeEst`, `isCron`, `simulateRateLimit`) instead of reading globals.
**You write:** extend `decide(message, state)`; extend the test table to cover every rule, local up/down, rate-limit on/off, and the four video prompts.
**Check:** all tests pass; you can explain why privacy is rule 1.
**Questions:** Why does "plan" need a word boundary? What should happen to a private message when the cloud is rate-limited?

### Lesson A7: Health poller (1 h)
**Goal:** the router knows within ~20 s when Ollama goes down or comes back.
**Concepts:** `setInterval`, `fetch` with `AbortSignal.timeout(3000)`, debouncing (two failures before "down"), cached state, cleanup on shutdown.
**You write:** `router/src/health.ts` exporting `startHealthPoller(url, onChange)` and `isLocalHealthy()`.
**Check:** quit Ollama → one `health` line "down" within 20 s; reopen → "up" within 10 s.
**Questions:** Why must the hook never `await` the health check?

### Lesson A8: Held reply (45 min)
**Goal:** private message + local down → friendly held reply, sent to no model.
**Concepts:** the `before_agent_reply` claim hook, synthetic replies, proving no model ran.
**You write:** register the hook; when `decide()` returns `held`, short-circuit with the held text and log `target: "held", model: "none", ok: false`.
**Check:** with Ollama quit, "This is confidential: …" gets the held reply; no ChatGPT turn appears.
**Questions:** How do you prove to a grader that the message reached no model?

### Lesson A9: Result logging and rate-limit flag (1 h)
**Goal:** a `route_result` line that shows what actually ran; a reversible rate-limit switch.
**Concepts:** observation hooks, linking decision and result by requestId, plugin config read at runtime.
**You write:** result hook + `logResult()`; read `simulateRateLimit` from plugin config.
**Check:** each message has decision + result lines with the same requestId; toggling the flag changes routing without a restart.

### Lesson A10: Forwarder (guided, 1–1.5 h, before the first deploy)
**Goal:** container-side Ollama traffic goes through Tailscale's SOCKS5 proxy, and every call is logged.
**Concepts:** HTTP proxying, streaming responses, SOCKS5 (`socks5h` means DNS is resolved by the proxy), why OpenClaw's own proxy settings were not enough.

## How to ask for help in OpenCode

- `/lesson A2` starts a lesson: explanation, concepts, skeleton, and the check.
- `/hint <what you are stuck on>` gives the next hint level, not the answer.
- `/explain <file, line, error, or concept>` explains without changing anything.
- `/review <file>` reviews your code against the spec, with questions first.
- `/done <task>` records the verified result in PLAN, STATUS, and PROCESS_LOG.
- Switch to the **mentor** agent (Tab) for discussion; it cannot edit files.
